
- Menu access is per member: a stored custom menu list replaces the role defaults; admins and Settings are always allowed. Why: lets admins tailor access without new roles.
- Keep Hostinger's Apache SPA fallback in public/.htaccess so Vite copies it into deployment output; Lovable hosting needs no redirect configuration.
- Keep package-lock.json synchronized with package.json after dependency changes because Hostinger installs with npm ci and rejects mismatches.
- Invoice saves compensate completed inventory writes on document-write failure using saveWithRollback; this prevents failed saves from leaving stock deducted, but is not a database transaction.
- Proposal payback uses the shared DISCO tariff (one global row, refreshed by the electricity-tariff server function at most weekly, validated before saving); bill math lives in src/lib/electricityTariff.ts. Why: rates change often and every proposal should pick them up without code edits.
- Report 148 uses the isolated stockValuation helper for purchase average and remaining-stock FIFO average, aggregating merged product IDs and using bills only when PO history is absent; other reports retain their existing costing.
- Proposal topics start at page boundaries with printable-height cover dimensions and separate quotation terms; tables may continue with repeated headings. Why: variable content must not create blank pages or detached signatures.
- Proposal covers use reference-derived static artwork with live HTML project/contact/detail fields and print-time text fitting. Why: retain the supplied design without baking another customer's details into new proposals.
- Proposal display options live in the existing proposal data JSON; duplication and printable pricing use proposalOptions helpers. Why: copies preserve options without schema changes and hidden pricing never alters saved costs.
- Proposal item research is identity-bound JSON metadata fetched by the authenticated product-specs function through Parallel search and the shared AI provider for evidence extraction; print only evidence-backed saved facts, never category defaults. Why: changing a product must not retain another product's specifications.
- Proposal voice conversations use the authenticated proposal-assistant function and validated field patches; only the existing Save action persists proposals. Why: spoken requirements need follow-up questions and explicit review without automatic writes.
- Independent WhatsApp proposal delivery uses company-scoped encrypted Meta credentials and approved document templates; after new proposal saves, server-side enable checks, customer consent and unique delivery claims prevent unauthorized or duplicate sends. Never resend edits or duplicates automatically, and report API acceptance separately from delivery confirmation.
- Bill extraction and proposal planning use the shared proposal-planning validator; system choice is explicit, catalog selling prices are resolved server-side and accessory estimates stay marked for review. Why: bills, assumptions and AI guesses must not become unverified consumption, engineering or prices.
- Proposal voice capture auto-submits after speech silence or manual stop, with audio unlocked during the initial user gesture. Why: avoid stuck listening and blocked browser playback.
- AI assistants, quotation parsing, tariff extraction and voice share company-scoped encrypted provider credentials through authenticated server helpers; only admins manage keys, quota exhaustion switches providers, and denials/invalid keys stop. Why: consistent private Settings controls without bypassing provider restrictions.
- Voice fallback is capability-aware: skip providers lacking Urdu synthesis or file support, never drop attachments silently, and retain legacy voice endpoint names for deployed clients. Why: keep provider switching accurate and backwards-compatible.
- Deploy proposal-assistant and its shared validator to the same backend used by each hosting environment, with Gemini credentials stored server-side and user validation enabled; never call Gemini directly from the browser. Why: independent hosting must work without Cloud bridges or exposed private keys.
- Customer-linked search uses the shared search helper with exact normalized name/company-label aliases to expand contact and CNIC fields; never fuzzy-match identities. Why: legacy sales documents store customer names rather than customer IDs.
- Global customer/document search passes search and tab query parameters to the existing lists and observes menu access. Why: searches from any page reuse the same results without exposing restricted destinations.
- CNIC taxation reporting uses exact customer aliases and saved tax reversal; product filters allocate saved invoice discounts/tax proportionally to selected lines and saved bundle component weights, never whole mixed invoices. Customer popovers use those same filtered product details; other tax reports remain unchanged.
